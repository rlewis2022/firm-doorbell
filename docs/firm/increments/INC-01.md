# Increment card INC-01: the Doorbell rings from flash

- **Backlog item:** rank 1 (Decide §5): button wake plays the built-in sound from flash, then sleeps.
- **Requirement:** when the Doorbell wakes from a button press, or from power-on or reset, it plays the
  built-in ding-dong from flash, then goes back to deep sleep. The sound comes first: nothing else runs
  before playback starts (A-05). Power-on chimes on purpose: it tells the user the unit works, with no
  LED drawing power (DL-023).
- **Increment type:** behavior change.
- **Acceptance criteria:**
  1. [Local] A button wake plays the built-in sound first, exactly once, then sleeps. (AC1)
  2. [Local] The sound played is the built-in sound the logic was given. (AC2)
  3. [Local] A power-on wake also plays the built-in sound once, then sleeps. (AC3)
  4. [Local] Any other wake goes back to sleep without a sound. (AC4)
  5. [Local] If playback fails, it still goes to sleep. (AC5)
  6. [Local] A held button gives one sound; it sleeps only after release. (AC6)
  7. [Local] A stuck button gives up after 10 s and sleeps. (AC7)
  8. [Gate, existing] `src/sounds/builtin_dingdong.h` is generated from `sounds/builtin_dingdong.wav`
     and the WAV meets B-02 (A-06). Firmware stays within B-01 (estimate ≈ 439 KB, 28%).
  9. [Real] RT-01 press-to-sound ≤ 300 ms (B-03), warning line 240 ms.
  10. [Real] RT-02 wake, play, sleep: power-on chime, 10 presses = 10 chimes, a 5 s hold = one chime.
- **Simulated tier:** none for this increment. Wokwi doesn't implement I2S on the ESP32-S3 (verified
  2026-10-27), so audio and wake are proven at the Real tier.
- **Protected behavior:** all absolutes; the existing Local test (`tests/local/test_main.cpp`).
- **Risks:** a button that stays pressed (stuck or iced) wakes the chip again as soon as it sleeps, so
  it rings about every 13 s until released (AC7 limits each wake to 10 s). Handling a stuck button
  properly needs a different wake setup: a backlog item, not this increment. Boot time before the app
  starts was never measured, so B-03 is a real unknown until RT-01 runs.
- **Files in scope:**
  - `sounds/builtin_dingdong.wav` (lock commit; made by `tools/make_builtin_chime.py`, DL-022)
  - `firmware/doorbell/src/sounds/builtin_dingdong.h` (generated by `tools/wav2header.py`)
  - `firmware/doorbell/src/logic/ports.h`, `src/logic/ring/ring.h` (declarations, lock commit)
  - `firmware/doorbell/src/logic/ring/ring.cpp` (lock-commit stub; generation replaces the body)
  - `firmware/doorbell/src/hw/` (I2S playback, deep sleep and button wake on GPIO2)
  - `firmware/doorbell/doorbell.ino` (wiring only)
  - `tests/local/locked/test_inc01_ring.cpp`; `tests/real/RT-01-press-to-sound.md`,
    `tests/real/RT-02-wake-play-sleep.md`
- **Fits the mold?** Yes. No absolute or budget changes.
- **Checks locked:** lock commit on branch `inc/01-ring-from-flash` (hash in the run log). Lock run:
  all 7 new Local checks compiled, ran and failed on their assertions against the stub; none passed,
  so none was reclassified as protected behavior.
- **Real-tier procedures required:** RT-01, RT-02.
